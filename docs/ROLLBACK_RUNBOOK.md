# AI DIGITAL SINAI — دليل التراجع

## متى نبدأ التراجع

ابدأ التراجع بعد موافقة قائد الحادثة عند وجود عطل حرج، مثل:

- فشل readiness أو startup بعد النشر.
- أخطاء متكررة في المسارات الأساسية أو عزل المستأجرين.
- فقدان أو تكرار أحداث الدفع أو قيود الدفتر المالي.
- تسرب سر أو بيانات حساسة.
- تجاوز SLO المعتمد دون تحسن سريع.

## قواعد أساسية

- لا تستخدم `git reset --hard` أو force push.
- لا تنفذ `DROP` أو rollback عشوائيًا على قاعدة الإنتاج.
- لا تعكس migration غير قابلة للعكس؛ استخدم forward migration معتمدًا.
- لا تعالج فشل الدفع بإعادة إرسال عشوائي؛ استخدم provider reference وidempotency وreconciliation.
- لا تُكشف الأسرار في السجلات أو أوامر الطرفية.

## خطوات التراجع عن التطبيق

1. افتح سجل الحادثة وحدد SHA الحالي وSHA الأخير السليم.
2. أوقف نشر traffic الجديد أو قلّله حسب قدرة المنصة.
3. أوقف worker أو queue consumer فقط إذا ثبت أنه يكرر أثرًا أو يعالج بيانات غير آمنة.
4. انشر آخر artifact سليم موثقًا، ولا تبنِ artifact جديدًا أثناء الحادثة.
5. شغّل `/api/health` ثم `/api/readiness`.
6. نفّذ smoke غير مالي.
7. راقب queue وwebhooks وpayment status وledger.
8. طابق عمليات الدفع مع مزود الدفع قبل إعادة فتح traffic.

## قاعدة البيانات

- إذا كان التغيير متوافقًا مع النسخة السابقة، أعد التطبيق فقط.
- إذا أضيفت migration غير متوافقة، نفّذ forward migration مصححة بعد مراجعة.
- استخدم backup معتمدًا فقط عند وجود فساد بيانات أو قرار استعادة رسمي.
- يجب أن تكون الاستعادة إلى Target منفصل أولًا للتحقق من checksum، schema، tenant isolation وledger integrity.

## بعد التراجع

- تحقق من readiness وcritical smoke.
- افحص عدم وجود قيود دفتر مكررة.
- افحص أحداث webhook المعلقة والمكررة.
- افحص رسائل Redis والـDLQ إن وجدت.
- وثّق السبب، المدة، الأثر، وقرار إعادة النشر.
- لا تُغلق الحادثة قبل reconciliation ومراجعة ما بعد الحادثة.
